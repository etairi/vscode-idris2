## Deviations from ROADMAP §5 M3

What the code does differently from the milestone text, and why:

- **Acceptance text.** The fixture's name is `greeting`, not `greet` (hover `Foo.B.greeting :
  String`). `putStrLn "hi"` alone does not type-check — `Can't find an implementation for HasIO
  ?io.`, since nothing fixes its monad [live, transcript `eval-values`] — so the IO action
  evaluated is `the (IO ()) (putStrLn "hi")`, which shows `MkIO (prim__putStr "hi\n")` and prints
  nothing; the bare form shows the compiler's error as the answer. `literate/Lit.lidr` does not
  exist; the `.lidr` of the acceptance is `loose-file/Lit.lidr`. "A replay whose
  `:highlight-source` frames carry empty `:type`/`:doc-overview`/`:namespace` fields (they all do,
  F33)" holds for `:type` and `:doc-overview` only: `:namespace` is empty on bound and declaring
  occurrences, and names the module on others (in `shapes-lookups` 32 frames `Foo.Shapes`, 11
  `Prelude.Num`, 2 `Prelude.Types` [live]), as F33 itself says; the replay tested hovers on
  `area`'s declaring occurrence, whose `:namespace` is empty (*Acceptance as tested*; corrected by
  the *Third review of M3*).
- **Document symbols come from M0's syntax model** of the text the editor shows, not from the
  token index: the index cannot tell an implementation header from a declaration (the interface
  name arrives with an empty namespace too [live, `shapes-lookups`]), and symbols then follow
  unsaved edits. Signatures (Function), data (Struct with Constructor children), records (Struct
  with Constructor and Field), interfaces (Interface with Method children), namespaces; `mutual`
  and `parameters` blocks flattened; implementations, clauses, fixities, pragmas and imports are
  not symbols. Only while the root's backend has `caps.documentSymbols`, and not for the fenced
  literate styles (M12).
- **Document highlights** group occurrences by name and decoration (as planned), but scope a bound
  name to its top-level layout block — its clause or signature, narrower than "the enclosing
  top-level declaration", which would join the variables of all clauses — and a global to the
  whole file (overloads of one name and decoration are not told apart either way). Without an
  index or a decorated name the provider answers nothing, and VS Code's word highlighting applies.
- **Inlay hints** mark only the first `:bound` token of each name per top-level declaration (a
  layout block), not every `:bound` token, which would repeat a variable's type after every use
  (seven hints on `append`'s signature instead of three). A second binder of the same name in one
  declaration (shadowing, another `case` alternative) gets none. While the document has unsaved
  changes they are not skipped (ROADMAP: "skipped while the document is dirty") but shown from the
  answers kept for the saved file, at the places their tokens were carried to, without new
  requests (*Inlay hints*; since the *Third review of M3*, for the layout shift at each
  keystroke). The price: a type that the edit changes (a signature being edited) shows as last
  checked until the save, as the hover shows it, with its stale note. This is a choice the user may
  revert to the ROADMAP's rule.
- **Type at Cursor** runs the hover's queries in command mode (loading the file if needed) and
  then shows the hover at the cursor (`editor.action.showHover`), not a notification, which would
  join the lines of a multi-line answer. **Docs at Cursor** opens the whole `:docs-for` answer in
  the `idris2-doc:` document; **Show Documentation…** asks for a name (the one at the cursor
  suggested; its title gained the ellipsis). Docs at Cursor refuses a local variable.
- **The doc overview** is the first paragraph of the user's docstring in the one `:docs-for` block
  whose declared name matches the type answer (the compiler ignores the overview mode, F31): the
  indented lines after the declaration line, up to a blank line or one of the compiler's section
  headers. Heuristic: a docstring line that itself starts with such a header ends it early.
- **The `eval` session** has its own build directory, `build/.vscode-idris2-eval` (ARCHITECTURE
  §5.2 said "same as `check`"), counts towards `idris2.ideMode.maxSessions` while idle and is
  evicted before any `check` session, is stopped — not restarted — by Restart Backend and by a change of its
  command line, is not restarted after an unexpected end (ARCHITECTURE §5.1's backoff applies to
  `check` sessions only), stops after 2 minutes idle, has its own time limit
  (`idris2.eval.timeout`), and loads the file before every evaluation (*Evaluation*; the last
  four since the *Review of M3*).
- **`idris2.keybindings.scheme`** has the default `auto` (VS Code has no per-platform setting
  default): `chords` on macOS, `prefix` elsewhere (*Keybindings*).
- **Interface** (ARCHITECTURE §3.1): the queries take the document (`docsFor(doc, …)`,
  `browseNamespace(doc, …)`, `evaluate(doc, …)`), M3 adds `completions` and `tokens`, `evaluate`
  answers an `Evaluation`, `TypeInfo` carries `lookup`, and `core/errors.ts` gains `NotLoaded`.
- Not created: `idris2.inlayHints.multiplicities` (no multiplicity hints in M3, ROADMAP M3 Out).
- **Since the *Review of M3*:** Go to Definition on a local variable shows no hint (ROADMAP: "a
  one-time hint"; VS Code asks the provider on a Cmd-hover too, *Untrusted text*); inlay hints are
  asked for the range VS Code asks about, which is larger than the visible one (*Inlay hints*); a
  setting the plan did not have, `idris2.eval.timeout`, bounds an evaluation (*Evaluation*); the
  doc overview in the hover is a plain code block, not escaped text (*Untrusted text*).

## Queries

- **Contract** (`backend/types.ts`, `IdrisBackend`, *Queries*). `typeAt`, `docsFor`,
  `definition`, `completions` and `browseNamespace` are answered by the root's `check` session in
  the context of the file it loaded last (the compiler keeps one loaded file, and a positional
  request refers to that file's text, F2). The backend notes each `:load-file` it sends (a
  `LoadRecord` per `LoadedFile`); a query whose document is not the session's last answered load —
  another file, a raw request, no process — rejects with `NotLoaded` at once, sending and starting
  nothing, and checks again right before the write (`beforeSend`). A query never loads: a load may
  compile and its diagnostics must reach the checks (F7). `typeAt` and `docsFor` are cached per load,
  and since the *Fourth review of M3* so are `definition`'s `:name-at` answers and target files.
  Queries take no cancellation token: a query VS Code cancelled while it waited behind a load is
  still sent (about 1 ms each, *Review of M3*, not changed).
- **`DocumentQueries`** (`features/intelligence/queries.ts`) loads on `NotLoaded` the way Check
  File does (`checks.check`) and asks once more — or, when a check of the document is already
  running (the one its opening started, still classifying the file), waits for that check instead
  (`DocumentChecks.runningCheck`, since the *Re-integration after the third review*: before, a
  hover right after a file was opened made a second `:load-file` of it once the first was answered
  [live, the packaged-extension check]). A passive query (hover, inlay hints, completion,
  definition) loads only the active document, only while its root's backend is `none` or
  `active` (never after Stop Backend, a give-up or a refused folder), and not under the `manual`
  trigger. Queries that need a load at once share one check. `AnswerCache` keeps answers per file
  until a load of any file of the root that may have changed what the compiler answers
  (`LoadedDocument.rebuilt`: a module was built, the load failed, or it was its process's first
  load), and until the document closes (`queries.ts` `StaleAnswers`; completion and inlay hints
  keep theirs the same way). Before the *Review of M3* a file's answers stayed until that file was
  loaded again, so the answers about a file importing an edited, saved and loaded module stayed
  stale; and a reload that built nothing dropped them.
- **`BackendRegistry.onDidChange` fires twice per IDE-mode request** (each state change of a
  `check` session: `ready` → `busy` → `ready`) [src, `session.ts`, `pool.ts`, `IdeMode`], so no
  provider refreshes or clears a cache on it; they follow `onDidLoad`. The integration removed
  `onDidChange` from `IntelligenceDeps.registry`, so a provider cannot subscribe to it.
- **`typeAt`**: positional `(:type-of "NAME" L C)` first, else by name. The compiler answers a
  positional request for whichever local is at the position, whatever NAME asks [live,
  `unicode-columns`: `(:type-of "y" 12 3)` → `x₁ : ℕ`], so an answer whose last line names an
  unqualified local other than NAME is not taken and the lookup by name is used; this also sends a
  method implementation's machine name (`perimeter_Measured_Shape`) to the lookup by name, which
  gives the declared type (`Foo.Shapes.perimeter : Measured a => a -> Double` [live,
  `shapes-lookups`]; `backendIde.test.ts` drives it through `IdeBackend` since the *Review of M3*,
  whose hover test and comment had said the machine name was shown). For a variable nothing is
  asked by name (since the review): the answer would describe a global the local shadows, which
  every caller drops. Whether the occurrence is a variable is the caller's to say (`decor`, the
  decoration its token index gives it) since the *Third review of M3*: the backend's own look-up of
  its index at the editor position cost O(tokens) per query (16,652 tokens on the 2,000-line module,
  18.8 ms per round of 138 inlay-hint queries [unit-level, the reviewer]) and, with unsaved lines
  above, found another token (*`definition`* below).
- **With unsaved changes** (*Third review of M3*). The compiler answers about the text its last
  load read (`LoadRecord.textBefore`), and the editor position is one of the text shown. While they
  differ, `typeAt` asks where the position lies in the loaded text (`core/positions.ts`
  `toLoadedPosition` over `lineCorrespondence`, a line diff since the *Fourth review of M3*: on an
  unchanged line the line it was, on a line edited in place — a changed line whose hunk has as
  many lines in both texts — its counterpart, only when that has the same text before the
  position, and on a line of a hunk that inserted or deleted lines none), converted with the loaded
  text's literate line map and code-point columns; a position that cannot be matched gets no
  positional request. Until the fourth review only the lines both texts begin and end with were
  matched, and a line between two separate edits was compared with the loaded line of the same
  number: with a line inserted at the top and the last line edited, the hover over `x` of `let x
  = the Nat 1` asked about the next line's `x` and showed `x : String` [live answers, the
  reviewer's probe]. Before, the
  request used the editor position and the shown text: with `f`'s clause deleted above `g n = n`,
  the hover over `g`'s `n` asked the saved file's line of `f`'s `n` and showed `n : Nat` for a
  `String` [unit-level, the reviewer's probe, answers recorded live]; below an inserted line a local
  got none; and a `.lidr` whose `> ` line was edited asked one compiler line too few. The hover
  keeps no type while the document is stale: its cache is keyed by the editor position, which then
  stands for another place of the file at each version, and an answer found so was shown after an
  undo back to the saved text [unit-level]. The backend keeps its answers per load and point sent. The hover drops a by-name
  answer for a `:bound` token and, while the document is stale, a positional answer that declares
  another name; it says "Name-based lookup: at this position the compiler gave no type of this name
  (none, or another name's), so it was looked up by name …" when the type was found by name (before
  the review: "found no occurrence at this position", untrue for the machine-name case; before the
  second review "the compiler gave no type for this name at this position", read as untrue when a
  neighbour answered), and puts "Results
  refer to the saved file as it was last checked" first while the document is stale (ARCHITECTURE
  §6.1). `typeAt` and `docsFor`, which keep answers per load, wait for a reload of the document's
  file that is being made (since the review: a hover during the check after a save showed the type
  before the save, with no stale note).
- **A name right after a local** (*Second review of M3*). The compiler's positional `:type-of`
  answers for a local whose span holds the position, and a span holds its end (`within`,
  `src/Core/FC.idr` 170–172; `processEdit (TypeAt …)`, `src/Idris/REPL.idr` 446–469 on v0.8.0

- **`definition`**: `(:name-at "NAME")` with the name unqualified (the qualified form answers `()`
  [live]; a qualified name keeps its own entries). An occurrence that the caller's token index

  F12 on `area` gave the saved file's (9,0)–(11,22), one line too high (the packaged-extension

## Token index

- Built from the `:highlight-source` frames of each answered `check` load of a document
  (`backend/ide/highlight.ts`), in one pass when the reply arrives (the session hands frames over
  with the `:return`); the frames' `:type` and `:doc-overview` are always `""` (F33), so it keeps
  name, decoration, span, namespace and the implicit flag. Frames naming another file are ignored
  (an imported module built by the load sends none [live, `load-simple-ipkg`]); entries sent twice
  are one token [live, `shapes-lookups`]; a decoration this version does not know, or a frame of
  another shape, is skipped. A load that returns an error sends none, and the previous index is
  kept. Every span goes through `core/positions.ts` with the text read from disk when the reply
  arrived (bird-track offset and literate line map, E14). The index is kept per document until its
  root is released: for every file with an open document, and for at most 16 others, those used

## Evaluation

- **The refusal** (`backend/ide/replCommand.ts`, ROADMAP §9 2026-09-28). IDE mode's
  `(:interpret "TEXT")` hands TEXT to the REPL's `interpret`, whose `parseRepl` reads it as a
  command when its first token after spaces and comments is the symbol `:` or `:?` [src, 0.8.0
  `15a3e4e` and master `1c630e6`, identical: `src/Idris/REPL.idr` 1138–1163, `src/Idris/Parser.idr`
  2333–2759, `src/Parser/Lexer/Source.idr` `lexTo`, `src/Parser/Lexer/Common.idr` 10–65; checked
  again by the integration]. The rule skips every leading Unicode white space, control and format
  character (a superset of the Prelude's `isSpace`, which U+00A0 belongs to), then refuses text
  starting with `:`, and text starting with `--` or `{-` that contains a `:` anywhere. It is at
  least as strict as the parser (the argument is in the module comment); it refuses more (type
  annotations after a leading comment, `::` at the start, a colon after U+3000/U+200B/U+FEFF).
  Recorded [live, `eval-command-forms`]: `:t id` ran as a command after a space, tab, CR, LF, VT,
  FF or U+00A0, after `{- c -}`, after `-- c` and a line break, and as `: t id`; it did not after
  U+3000, U+200B or U+FEFF, after `||| d` and a line break (parse errors), with U+FF1A for the colon,
  or as `:T id`. The refusal is the first thing `IdrisBackend.evaluate` does, before it classifies
  the file or asks for any session; NUL is refused too. The command itself finds the backend by
  classifying the file first (`ProjectIndex.classify`), which runs `idris2 --dump-ipkg-json`, a
  read-only query in the tool's own directory (M1), when the package's model is not cached — so a
  refused text can start that query, never an IDE-mode process (the wording "before the file is
  classified" was true of the method only; corrected by the *Review of M3*).
  `IdrisBackend.evaluate` is the only sender to the `eval` session.
- **What the compiler answers** [live, `eval-values`, `eval-socket`, and the e2e suite]: a value
  as it prints it (`[1, 2]`, `"hi!"`, `\x => plus x 1`); an IO action normalised, not run —
  `MkIO (prim__putStr "hi\n")`, with nothing unframed in the stdio stream and nothing on the socket
  process's stdout —; a type error or an undefined name as an error, which is an answer
  (`Evaluation.kind = 'error'`), not a failure.
- **The `eval` session** (`backend/ide/pool.ts`, `types.ts` `SessionRole`): started lazily at the
  first evaluation in its root, through the same trust, toolchain and consent checks before every
  spawn as the `check` session, in the same directory, with the same transport rule (stdio unless
  the user chose the socket); the load before an evaluation has `idris2.ideMode.longActionTimeout`,
  the `:interpret` `idris2.eval.timeout`. Its command line differs in one argument:
  `--build-dir <session directory>/build/.vscode-idris2-eval` whenever the `.ipkg` and `extraArgs`
  choose no build directory, whatever `idris2.ideMode.isolateBuildDir` says. Why: a load in the
  `eval` session that rebuilt a just-saved file into the `check` session's directory would make the
  `check` session's next load of it report nothing (F7), and the checks keep what such a load
  leaves shown [reasoned, not run]; and two processes would write one directory at once (E21). When
  the package or `extraArgs` choose the directory, both sessions share it — a documented limitation,
  as for the user's own builds. It counts towards `idris2.ideMode.maxSessions`: it loads the same
  modules as the `check` session (206–278 MiB on `contrib` for a `check` session,
  docs/measurements/first-load.md [live]; the `eval` session on the 2,000-line module: 191 MiB
  after its start, 206–210 MiB after the load, 247 MiB after six evaluations [live, *Second review
  of M3*, macOS `footprint`]) — but only while it is idle (since the *Fourth review of M3*: being
  started or evaluating, it counted, and with a limit of 2 an Evaluate in one project stopped

  idle `eval` sessions are evicted first — the active root's included, since with a limit of 1 the
  active root's two sessions would otherwise stay above it for good —, then `check` sessions of
  other roots. **It never starts a process by itself** (the *Review of M3*): Restart Backend — for
  one project, and, since the review, for all projects — and a change of its command line stop it
  (it starts again at the next evaluation; before, Restart for all projects and a settings change
  started a new, idle `eval` process at once), and an unexpected end — an exit, a time-out, a
  protocol error — leaves it `stopped` with every waiting request rejected, instead of restarting
  it after the backoff (before, a time-out of a runaway evaluation started a new process at once,
  idle for up to 10 minutes, and a fourth end within five minutes left it `failed` for good). Stop
  Backend, release, a changed package, a revoked folder and a cancelled evaluation stop it too, and
  it stops after `EVAL_IDLE_TIMEOUT_MS` (2 min) without a request, or after
  `idris2.ideMode.idleTimeout` if that is shorter (0: never). **After an evaluation whose
  `:interpret` took more than `EVAL_RELEASE_AFTER_MS` (1 s)** it is stopped too, once it has
  answered (`SessionPool.releaseEvaluation`, cause `stop`; since the *Second review of M3*): the

  could not be started, a handshake it cannot read, a socket another program may have taken)

  and compiler lines, which may hold bidirectional controls. Go to Definition on a local variable
  shows nothing (it showed a one-time hint): VS Code asks definition providers while the mouse
  passes over a word with Cmd or Ctrl held (`startFindDefinitionFromMouse` [src, the 1.139.1
  workbench bundle]), so the hint came from a gesture that asked for nothing, and used itself up.

## Completion

- Keywords (the lexer's 41, `KEYWORDS`, exported from `features/syntax/lexer.ts`), the 46
  `%`-directives the parser accepts (checked against the grammar's list), and the compiler's names
  for the identifier being typed (no kind: the reply says nothing about what a name is). After `.`
  or `?` names only; nothing inside a number or a character literal, or on a bird-track prose line.
- **Never blocking**: after each load of the active document's file, `IdeMode.warmUpCompletions`
  sends one `(:repl-completions "zq")` (a prefix that matches nothing; any prefix warms the next
  completion — *Measured*), once per load and not after a real completion; and the provider waits
  at most `COMPILER_WAIT_MS` = 150 ms (a choice between the measured steady state, p90 ≤ 10.8 ms,
  and the first request after a load, 113 ms and more; not itself measured), then answers the
  keywords with the list marked incomplete, so the next keystroke asks again. Answers are kept per
  file until a load of the root makes them stale or the document closes (*Queries*); a longer
  prefix is answered by filtering a kept shorter one, and, since the *Review of M3*, one typed
  while a shorter one is still asked waits for that request instead of queueing its own (the
  review counted five requests for five keystrokes behind a 600 ms first request [unit-level]).
  The
  warm-up costs the `check` session about 0.2 s after each load of the active file — and it made the
  M2 diagnostics tests that expected a session to be `ready` right after Check File fail until they
  waited for it (*Integration*). Since the *Third review of M3* it is sent only once the session has
  been idle — nothing in flight or queued — for `WARM_UP_QUIET_MS` = 150 ms (checked again at that
  interval; not sent when that has not happened within `WARM_UP_MAX_WAIT_MS` = 10 s, or when the
  session loaded another file or ended meanwhile; both constants a choice). Sent at once, it went
  before the query that had waited for the load (a hover, Type at Cursor, Go to Definition or the
  first inlay hint of a file whose load had just been answered, and a hover during the check after
  a save), which then waited behind the slow first completion [unit-level, the reviewer's probes:
  345 ms instead of about 201 ms with a 140 ms first completion].
- **Names as labels** (*Third review of M3*). A completion item's label is drawn by VS Code
  1.139.1's suggest widget with theme icons on (`IconLabel` with `supportIcons` [src]), and a name
  from the compiler is untrusted text — any character above U+00A0 is an identifier character, and
  an elaborator script makes any string a name: `(:repl-completions "vl")` answered `vlxyz` with
  U+202E and `ab`, and `vl$(zap)` [live, one `timeout 60 idris2 --ide-mode` on the reviewer's
  file]. So the label is `quickPickText(editorLabel(name))` and the `insertText` and `filterText`
  are the name itself.
- After a qualifier (`Data.Vect.fil`) completion offers every name in scope that starts with the
  last part, whatever its namespace (`:repl-completions` ignores namespaces [live, `clean-queries`]),
  so an item such as `fileSize` inserts `Data.Vect.fileSize`, which does not resolve (*Second review
  of M3*; documented in the README, not filtered: `:browse-namespace` of an alias or a namespace
  suffix was not tried).

## Inlay hints

`: <type>` after the first `:bound` token of each name per top-level declaration (*Deviations*),
from a positional `:type-of` whose answer is `<name> : <type>` (a by-name answer, or one about
another name, shows nothing); requests one at a time, only for the range VS Code asks about —
not the visible range alone, as this record said before the *Review of M3*: VS Code 1.139.1 asks
for the visible lines and a viewport's height of lines (at least 20) above and below them, widened
by 30 lines on each side (`getVisibleRangesPlusViewportAboveBelow`, `_getHintsRanges` [src, the
workbench bundle]), for a window of 50 lines about 210 lines, which on the e2e suite's 2,000-line
module the review estimated at about 140 positional `:type-of` requests —; kept until a load of the
root makes them stale or the document closes (*Queries*; also the answers that show nothing), so a
load that built nothing asks none of them again; nothing is asked while the document has unsaved
changes or shows another text than the index (*Token index*), and since the *Third review of M3*
the kept hints are shown then at the places their tokens were carried to (`currentTokens`, as the
semantic tokens are; a token not carried over gets none) — before, none were shown, and VS Code
1.139.1 replaces the hints in the range it asks about with the provider's answer and pads the line
with the cursor only for the hints the answer has there (`_updateHintsDecorators` [src]), so at the
first keystroke every hinted line moved left, and back after the save and the queries [src; not
observed in a running VS Code]; a query that is unavailable ends the round, and
the hints are asked for again at the next load and, since the *Second review of M3*, when an Idris
file's editor becomes the active one: VS Code 1.139.1 asks again on a provider's change, a model or
language change, the configuration, a scroll, an edit and a double click, not on focus
(`InlayHintsController` [src]), so the hints of the second of two editors side by side, whose kept
answers a load of the first dropped and whose passive query was refused while it was not active,
stayed missing until a scroll or an edit there [src, not run]. Since the *Fourth review of M3* a
load that makes a file's answers stale moves them aside (`lastKnown`, with the text of the index
they were asked with) instead of dropping them, and they are shown where nothing can be asked —
for tokens carried over while the document shows other text than the index, and for the tokens
left in a round a query ended unavailable — while the index is still of that text; a fresh answer
takes a token's place. Before, a save whose load failed (a failed load counts as `rebuilt` and sends
no highlighting, so the index stays and the saved text differs from it) and a load of another file
of the root that built something (the other editor's queries refused, not being active) emptied the
file's hints until a successful save or a focus, every hinted line moving left [unit-level, the
reviewer's probes]. Such a hint can be out of date where that load changed a type it depends on.
The tooltip has the answer in a code block. `idris2.inlayHints.variableTypes` (default on) and VS
Code's `editor.inlayHints.*` apply.

## Open issues

- **Q23** (ROADMAP §9, restated by the *Fourth review of M3*): whether Evaluate should keep
  elaborator scripts from running — the script of any `%macro` the expression applies runs without
  `%language ElabReflection`, and a textual rule could refuse `%runElab`, not a macro application
  (*Evaluation*, *Not refused*).
- Not checked in a running VS Code by a person: how hovers, the stale and name-based notes, inlay
  hints, the evaluation label and the docs document look; the keyboard shortcuts pressed; whether
  the evaluation hover shows over the label itself (`docs/checklists/M3.md`).
- E14 for `:warning` columns, CLI text and `:case-split` requests is [src] only; no recording has a
  warning or a case split on a line with a character outside the BMP.
- The `eval` session's memory is bounded by time only (*Evaluation*): after an evaluation of more
  than a second it is stopped; one of less keeps what it made the process take (not measured).
- **For the user** (*Review of M3*, not fixed): sending `(:enable-syntax :False)` once to each
  `eval` process before its first load would make each evaluation's load cheaper — on the e2e
  suite's 2,000-line module an unchanged reload took 283–310 ms with 16,652 highlight frames and
  112–166 ms without, and the extension host spent 53–93 ms decoding those frames [live and
  unit-level, the performance review] — but the CLAUDE.md M3 rule allows nothing but evaluations
  and their loads on the `eval` session. The decoding needed no such decision and is gone since the
  *Third review of M3*: an `eval` session drops those frames unparsed (`session.ts`, *Unread
  highlighting*; 77 ms of the extension host per evaluation of that module [unit-level, the
  reviewer's offline run]); the compiler's own time for them remains.
- The backend queries take no cancellation token (*Review of M3*): a query VS Code cancelled while
  it waited behind a load is still sent.
- An evaluation's memory is not sampled: the time limit and Cancel bound it by time only.
- The Linux list of E23 was not recorded (printed by the integration suite on ubuntu).
- `describesAnotherLocal` reads the answer's last line; an unrecorded shape (a binder in braces)
  could be misjudged and fall back to the lookup by name.
- The doc overview's end is heuristic when a docstring line starts with a section header.
- The inlay-hint rule gives no hint to a second binder of the same name in one declaration.
- The completion warm-up costs the `check` session about 0.2 s after each load of the active file,
  once the session has been idle for 150 ms; a hover made while it runs waits for it.
  `COMPILER_WAIT_MS` (150 ms), `WARM_UP_QUIET_MS` (150 ms) and `WARM_UP_MAX_WAIT_MS` (10 s) are
  choices, not measurements.
- The token index describes a text only when the file read the same right before the load and
  after it; a change and a change back in between (ABA) is not seen. A file changed on disk
  between the compiler's read and the extension's read after the reply still makes the
  diagnostics' positions off until the next load (as in M2); the index then has no text, and only
  its named tokens that the document still spells are used.
- Kept answers are dropped by loads of the `check` session only: where the package or `extraArgs`
  choose one build directory for both sessions, a load of the `eval` session (or the user's own
  build) that rebuilt a module there is not seen, and the next `check` load builds nothing —
  answers about files importing it stay until a load that builds something (D5's shared-directory
  limitation).
- An error answer to `:name-at` or `:browse-namespace` gives `[]`; none was recorded.
- In markdown-mode `.idr.md` files completion also answers on prose lines when invoked explicitly
  (fence detection is M12).
- From the *Second review of M3*: Org files (`.idr.org`) get the `#+IDRIS:` line marker's offset and
  line map, but not the model of their `#+BEGIN_SRC` blocks (E19, M12): a `#+IDRIS:` line inside a
  block is mapped as a marked line; completion, Evaluate Selection and the syntax model do not know
  the Org marker. The documentation document opens in another extension's language when that
  extension's `filenamePattern` matches its path (*Untrusted text*). After a qualifier completion
  offers names of every namespace (*Completion*). `IdeBackend.typeAt` asks one code
  point further only after a non-space character; a neighbour local on both sides (`x+y`) still
  ends in the lookup by name. M1's fallback `.ipkg` parser adds 1 to lines and columns outside
  `core/positions.ts` (ARCHITECTURE §2 notes it).
- From the *Third review of M3*: a CRLF literate file is not mapped (F11 addendum): a CRLF `.lidr`
  does not compile, and a CRLF fenced file (`.idr.md`) compiles with its compiler lines after
  prose smaller than its file lines, so its diagnostics, hovers, semantic tokens, inlay hints and
  definitions land on the wrong lines; the README asks for LF (mapping the fenced styles is M12's).
  With unsaved changes, `IdeBackend.typeAt` asks about a position on a changed line only when the
  line was edited in place and its loaded counterpart has the same text before it (since the
  *Fourth review of M3*; before, the loaded line of the same number); a name after a change on its
  own line gets no positional answer (a global is then looked up by name, and Type at Cursor on a
  local says that the compiler answers about the file as last checked). The inlay hints kept while the
  document has unsaved changes show the types of the last check, also where the edit changed one.
  Diagnostics show the compiler's messages with their invisible characters as sent (M2; the
  README says so since this review).
- From the *Re-integration after the third review*: the completion warm-up is sent after 150 ms of
  quiet also when the document has been edited meanwhile (harmless: it asks about the loaded file,
  as a completion would). A completion asked right after a load, before the warm-up, answers with
  the keywords alone, marked incomplete, when the compiler takes longer than `COMPILER_WAIT_MS`;
  the next keystroke gets the names. When a project is first classified, the extension's `idris2
  --dump-ipkg-json` of its `.ipkg` (M1) can run beside the `check` session that has just started
  (seen at the start of both runs of the packaged-extension check): the one-at-a-time rule of the process
  runner does not cover sessions (M2).
- From the *Fourth review of M3*: the line diff pairs no line of a hunk that inserts or deletes
  lines, so after Enter in the middle of a line (or two lines joined) that line's tokens and
  inlay hints go and a hover there gets no positional answer until the save; more than
  `MAX_LINE_EDITS` (1,000) lines inserted and deleted leave every line between the first and last
  change unpaired; where the edit makes it ambiguous (one of two equal lines deleted) a line is
  paired with the equal line the diff chooses; on a line edited in place a position at column 0
  always matches its counterpart (the hover drops an answer about another name, not about another
  binder of the same name). The inlay hints a load made stale (`lastKnown`) are shown where nothing
  can be asked and can be out of date where that load changed a type they depend on. The active
  document's check is started last among the visible ones, but its load is queued last only when
  the other files are classified first. Go to Definition keeps nothing in the provider any more:
  a Cmd-hover in an editor whose file another load replaced gets nothing, where it used to get a
  kept answer. Its namespace filter falls back to every entry when none is named `NS.name` or
  `NS.(op)` (an entry whose name the compiler prints otherwise is not told apart).
