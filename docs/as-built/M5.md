## Decisions

The user's decisions of 2026-10-01 (ROADMAP §9), as built:

1. **IDE mode stays the default (Q7).** `idris2.backend.mode` (`resource` scope): `auto` gives IDE mode
   to every root while a usable `idris2` exists or no trusted scan has finished, idris2-lsp to a root
   with an `.ipkg` only when `idris2` is not usable and the server is, and its pair verdict is not
   `likelyMismatch`; `lsp` gives idris2-lsp to every root with an `.ipkg`; `ideMode` gives IDE mode.
   **Switch Backend…** keeps a per-root choice in the workspace state (`idris2.backendChoices`), which
   comes before the setting. One backend per root, no secondary one, no fallback per feature
   (*Routing*). Choice made in the lane: an explicit `lsp` (setting or choice) is followed even on a
   `likelyMismatch` verdict, which M1's notification and the status report; only `auto` avoids a server
   expected not to work.
2. **pack outside `PATH`; the pair verdict.** The server is compared with the `idris2` in its own
   directory, as found (no symbolic links resolved): pack's wrappers sit side by side, and `make
   install` puts both into `~/.idris2/bin`. That compiler gets one extra `--version` probe (5 s limit,
   through the runner, never in Restricted Mode) when it is another file than the `idris2` the search
   found; with none beside the server, M1's pairing with the search's `idris2` stays, with its
   explanations (`toolchain/verdict.ts`, *Which compiler*). On the development machine pack's
   `idris2` (`0.8.0-1c630e67c`) against API `0.8.0-1c630e67c` is `compatible` [live, e2e-lsp], where
   pairing with Homebrew's `0.8.0` would read `likelyMismatch`. The tests name the server by path:
   `IDRIS2_LSP` for the e2e suite, `idris2.toolchain.lspPath` in the suites' settings. Discovery is
   unchanged: pack's bin directory is searched when `PACK_BIN_DIR` is in the Extension Host's
   environment or in `idris2.toolchain.env`, else `~/.local/bin` [live, file-system-only run of the
   discovery by the routing lane].
3. **M4's editing rules hold on LSP.** The server's edit is never applied as it is: the answer is taken
   out of it and handed, as IDE mode's reply, to IDE mode's plan (`backend/ide/edits.ts`), which applies
   always bracket, Make Case's bracketed template, the layout refusal, the clause, lemma and
   missing-case places and the literate markers; names are checked before anything is sent; the
   version check and the one undo step are `features/editing/apply.ts`'s, as in IDE mode (*LSP
   backend*, *Contract*). Where the server cannot give what IDE mode gives, the refusal says so:
   refine ambiguity (F34), Next Result after the server's `maxCodeActionResults` results, Proof Search
   without a result.
4. **Bounded reviews**: after this integration, fix rounds until one finds no high or medium issue (at
   most three), then one final review in which only high findings and regressions are fixed.

Design choices of the lanes and the integration (each with its reason in the module named):

- **Which features come from where** (`backend/lsp/middleware.ts`, `backend.ts`). The language client's
  own providers serve completion, hover, signature help, definition, document highlights and symbols,
  semantic tokens, the published diagnostics, and the server's quick fixes but Add Missing Cases; the
  extension's providers stay silent for those documents (`LSP_CAPABILITIES`). `LspBackend` answers the
  edits, the holes and the namespace listings. Not offered over LSP, each with a message: documentation
  (the server has no request for it), **Evaluate Selection** (the server's `repl` evaluates in the file
  it loaded last, which can be another open file's, and cannot be stopped without a restart: no
  `$/cancelRequest` handling in idris2-lsp `9a2f0ad` [src]), Type and Docs at Cursor (the hover answers),
  inlay hints.
- **What the library may do** (`client.ts`): only the text sync and the providers above are registered
  (`CLIENT_FEATURES`), so the server's `executeCommandProvider` commands do not become global VS Code
  commands a command link could run; the server's `workspace/applyEdit`, `window/showDocument` and
  dynamic registrations are refused, its window messages go to the output channel, never to a
  notification.
- **Reading the server** (`client.ts` `FramedMessageReader`): the extension frames the JSON-RPC stream
  itself, because a `%logging` pragma makes the compiler print `LOG` lines on the server's standard
  output, where vscode-jsonrpc 9.0.3's reader loses every later message [live, recording `logging`].
- **The process**: started through `core/process.ts` `startLongRunningProcess` from `ServerOptions` as a
  function, in the trusted workspace folder that holds the starting document's root (else the root's
  own folder, which the consent gate allowed), in the real path the gate judged right before the spawn;
  no arguments; the scan's `idris2.toolchain.env` over the Extension Host's. One server per window. M2's
  backoff: at most three restarts in five minutes (0 s, 2 s, 10 s), then `failed` with a warning.
  **Stop Language Server** leaves it stopped until **Restart Language Server**.
- **Text sync**: every change is sent as the whole text, although the server offers incremental sync:
  lsp-lib applies a range's `character` as code points and put an insertion after the last line break
  on the line above [live, `features-cross`].
- **Clean again** (integration): the server takes a document as changed from a `didChange` until a
  `didSave`, whatever the text, and answers `null` meanwhile [src, live]; when VS Code shows a document
  unchanged again without a save (an undo back to the saved text, a revert), the client sends `didSave`
  with its text (`middleware.ts` `DocumentSync`, *Clean again*).
- **The consent question** for a root routed to idris2-lsp is asked when one of its documents is shown in
  a visible editor (`features/backend/follow.ts`), as IDE mode's checks ask; `LspOwnership.admits`
  never asks. A document opened but never shown never reaches the server.
- **The missing-`.ipkg` notification** is decided client-side, once per root and window, offering **Use
  IDE Mode for This Folder** when `idris2` is usable; the safety net (*Deviations* 2) gives the same
  notification.
- **Restart Backend** refuses, with a message, a root IDE mode does not serve (`extension.ts`), so it
  cannot start a second compiler for an idris2-lsp project.
- **Restart questions**: the language client asks once when a new toolchain scan finds another
  `idris2-lsp` or another environment than the running server's (`idris2.toolchain.lspPath`, `env`,
  `preferPack`); `features/backend/restart.ts` asks when `idris2.lsp.logFile` is cleared (the server
  cannot go back to its standard error). `idris2.lsp.trace.server` asks nothing: vscode-languageclient
  re-reads it at every configuration change and sends `$/setTrace` [src: 10.1.2 `lib/common/client.js`
  1498–1534].
- **Settings** (prep): the eight server options with the server's own defaults read in its source
  (`logSeverity` `debug` — since 2026-10-24 `info` here, the user's decision: at `debug` the server logs
  every message it receives whole, `Received message: …`, `Server/Main.idr` 94 [src], the files' text
  included; at `info` and above only paths, methods, settings and errors —, `longActionTimeout` 1000 ms, `maxCodeActionResults` 5, the four booleans
  off; `logFile` empty = standard error), `window` scope but `logFile` (`machine-overridable`, in
  `restrictedConfigurations`: the server creates folders and appends to the file); `trace.server`
  `messages`|`verbose` (no `off`: the library writes a trace only while its channel's level is Trace,
  and then reads `off` as `messages`), read by the library itself under the client id `idris2.lsp` —
  the one setting not read through `core/config.ts` (`test/unit/manifest.test.ts` lists it).
- **bamboo's settings** (`features/backend/migration.ts`, F36): offered in a trusted workspace at
  activation and on any `idris2-lsp.*` change, once per distinct plan per window, **Don't Ask Again**
  in the global state. Key map: `loglevel → idris2.lsp.logSeverity` (lower-cased, one of five);
  `logFile`, `longActionTimeout`, `maxCodeActionResults`, `showImplicits`, `showMachineNames`,
  `fullNamespace`, `briefCompletions` → `idris2.lsp.<same>`; `path → idris2.toolchain.lspPath`;
  `trace.server → idris2.lsp.trace.server`. Not copied, the reason shown: a `logFile` of `stderr` or
  a path neither absolute nor `~`-prefixed, a trace `off`, counts below 1 (fractions rounded down),
  wrong types, and a workspace folder's value of a `window`-scoped key (VS Code writes folder values of
  `resource`, `language-overridable` and `machine-overridable` settings only [src: VS Code 1.140.0
  workbench bundle, the configuration-editing scopes 5–7]). Only values the user set are copied, into
  the same scope, where ours has none; bamboo's are left. bamboo facts [src: `bamboo/idris2-lsp-vscode`
  `1e93392`, `package.json` 0.7.2 (`loglevel` enum, `logFile` default `stderr`, `briefCompletions`
  default true, `longActionTimeout` default 5000), `src/extension.ts` 59–60]. The integration removed
  the lane's internal command that copied without asking (no caller; a command link could have run it).
- **Holes view over LSP** (integration): the holes model refreshes after the server publishes a document's
  diagnostics, which it does after each load of the file (`LspClient.onDidLoad`), as after IDE mode's
  loads.
- **A root leaving IDE mode** (integration, the routing lane's request): its waiting checks are dropped,
  its sessions stopped and the problems IDE mode set for it removed (`DocumentChecks.forgetRoot`), so the
  Problems view shows the server's alone.

## Deviations from ROADMAP §5 M5

1. **`browseNamespace`** answers `SymbolInformation[]` (`name` = `<name> : <type>`, private names and
   names without a location left out), not `[string]` [src `Language/LSP/BrowseNamespace.idr`; live].
2. **F35's safety net.** The code-3 `Cannot find the ipkg file` error and its `Cannot load ipkg file for`
   log line cannot occur with Idris 2 `1c630e6`, whose `findIpkg (Just f)` returns the file itself when
   it finds no `.ipkg` [src `Idris/Package.idr` 1093–1110]. What occurs [live, `loose-file`]: `didOpen`
   publishes nothing and logs `LOG ERROR:Server: … Source file "<abs>" is not in the source directory
   ""`; a request about a file never opened answers that text with code **4**; one about an opened file
   answers `null`/`[]`. An `.ipkg` deleted while the server runs is not reported at all: loads go on
   with its options and write TTCs beside the sources [live, `ipkg-deleted`]. The client reports both
   forms, the error of any request (seen in the middleware's request hook, below the library's
   providers, which turn a failed request into an empty answer) and the log line; the ROADMAP's
   integration criterion (code 3) is tested with the fake's fault, the live form by unit tests.
3. **`lsp.trace.server`** prompts no restart (above), and has no `off`.
4. **A dirty document's semantic tokens**: the server's `RequestCancelled` becomes a
   `CancellationError`, after which VS Code keeps the tokens it shows [src: VS Code 1.140.0 workbench
   bundle]; returning the last tokens (ARCHITECTURE §5.3) would set tokens of the text before the
   unsaved edits.
5. **No IDE-mode fallback per feature** (decision 1; ROADMAP M5 *Risks* and *Scope* named one).
6. **Evaluate over LSP is not offered** (above); `repl` text is still refused by M3's
   `replCommandRefusal` in the client, since E10 showed that `repl` runs colon commands.
7. **The consent question** is asked when a document is shown, not when it is opened.
8. **The restart question for `toolchain.lspPath`** is asked by the language client when the new scan
   finds another executable or environment; one question per change (the first integration run showed
   two, the client's and `restart.ts`'s).
9. **Stop Language Server** leaves the server stopped until Restart (the ROADMAP leaves it open).
10. **The no-`.ipkg` notification** offers IDE mode only (M11's scaffold does not exist).
11. Activation events and `contributes.semanticTokenTypes` needed no change: M0 has the four activation
    events and contributes `module` and `postulate`, the server's two non-standard token types.
12. **The mismatch e2e** asserts M1's one-time `pairMismatch` notification (the "banner").

## Language client

`backend/lsp/client.ts`, `middleware.ts`, `commands.ts`; the module comments hold the reasons.

- **Ownership**: `DocumentSync` keeps the set of documents the server has open. `didOpen` is forwarded
  only when `admits` holds, `didChange`/`didClose` only for an open document, `didSave` only for an open
  one still admitted; on `LspOwnership.onDidChange` the sync opens and closes documents to match, clearing
  the diagnostics of those it closes. Every provider hook answers nothing, without asking the server,
  for a document not open and admitted. Below the hooks, the general `sendNotification`/`sendRequest`
  hooks are a last check: a `textDocument/*` notification passes only for a document the sync is
  opening, has open or is closing; a request naming a document (also inside `workspace/executeCommand`'s
  `codeAction` argument) only for an open, admitted one. Requests matter as much as `didOpen`: any
  request about a file loads it, also one never opened [live, `features-cross`].
- **Coordinates**: the server reads and writes the compiler's coordinates (0-based compiler line, code
  points of the unlit text; [src `mkLocation'`, `findPointInTreeLoc`; live `lit2`]); completion reads its
  own copy of the file by file line and code points. Every position goes through `core/positions.ts`
  both ways: hover ranges, definitions (another file's with its open document, else its text on disk),
  highlights, symbols, semantic tokens, diagnostics, quick-fix edits.
- **Untrusted text**: hovers are rebuilt as `MarkdownString`s that are not trusted, without HTML or
  icons, holding only `codeBlock`s (the server's `idris` fence becomes an `idris2` block of the type);
  completion labels and details `editorLabel`/`quickPickText`, documentation `visible` plain text;
  signature help likewise; symbol names `editorLabel`; quick-fix titles `quickPickText(editorLabel(…))`.
  Completion items and code actions are rebuilt without their `command` and `additionalTextEdits`; a
  quick fix keeps only an edit of its own document, is kept only when its kind is `quickfix` and its
  diagnostic is one VS Code passed (the server answers every stored fix for any position, F28 [live]),
  and none is offered in a bird-track or Org file (the server's new text lacks the line markers [live,
  `lit2`]).
- **Output**: the server's standard error goes to the channel "Idris 2 Language Server" line by line at
  the level its `LOG <SEVERITY>:` names (so `DEBUG` lines appear once the channel's level is Debug),
  control and format characters written out; stdout bytes that are not a message are written there too.
- **Commands**: Restart, Stop, Show Output; **Send Raw LSP executeCommand…** only while
  `idris2.trace.protocol` is on in a trusted workspace, about the active document, its text typed by the
  user (an argument is taken only under the test runner), the answer written to the channel.

## LSP backend

`backend/lsp/backend.ts`, `edits.ts`, `holes.ts`; `edits.ts`'s module comment lists each kind's request,
title and how its answer is read.

- **Edits** follow ARCHITECTURE §3.3's mapping (`context.only` = the specific key, the action chosen by
  its title, `exprSearchWithHints`/`refineHole` through `executeCommand`, Add Missing Cases through the
  quick fix with the coverage diagnostic), then *Decisions* 3. An edit is asked only for a `file:`
  document still at the request's version, without unsaved changes, whose lines are the file's on disk
  (the server reads the disk); the server's `null` is `DirtyDocument`. Commands that name no document
  (`metavars`, `browseNamespace`, `refineHole`, `exprSearchWithHints`) are sent after a
  `textDocument/documentSymbol` of the document, which makes the server load it.
- IDE mode's `holeRefusal` (one hole of the name at the cursor) is not applied: the server finds a hole
  by its position, and told apart two holes `?todo` of two modules [live, `holes-ipkg`], where IDE mode
  refuses. IDE mode's refusal after a load with errors (F16) is not applied either: the server answered
  Add Clause on `Part.idr` with its two coverage errors [live].
- **Searches**: Proof Search and Generate Definition keep the server's up to `maxCodeActionResults`
  results; Next Result / Next Definition apply them in order and then say that the server gives no more
  than that setting (or `exhausted` when it gave fewer). The server's `Generate next definition`
  answers the first definition again at every request [live], so it is not used.
- **Holes**: `metavars` → `Hole[]` by IDE mode's rules (declarations without clauses left out, the
  holes of imported modules kept); positions from the files as the server read them; premises have no
  location (F26 corrected) and multiplicity `Rig0`/`Rig1`/`RigW`. Asked once more when the answer
  locates none of the document's holes while its symbols show some (another file's request came between
  the two requests).

## Contract

`test/unit/contract.test.ts`: the same request on byte-identical fixtures (`broken/<F>` in IDE mode,
`lsp-ipkg/src/<F>` over LSP), answered from the IDE-mode transcripts of idris2 0.8.0 and from the
recordings of idris2-lsp, gives the same `EditResult` — the same text in the same place, or the same
refusal — for 66 requests on `Clean.idr`, `Edits.idr` (shapes, searches, primed and non-ASCII names),
`Lit2.lidr`, `Ambig.idr` and `Part.idr`, plus 7 both backends refuse and Proof Search's next results
(0, 1, 2 on `?vlen_rhs`, the same order, E24): 80 tests with the 6 below. Where they differ, each
difference is a test of its own:

- **Generate Definition / Next Definition**: the server lists the compiler's first
  `maxCodeActionResults` definitions unsorted, IDE mode sorts 16 (`makeDefSort`); the first is the same
  for `append` and `swap` and differs for `zip3` and `(<||>)`; `append`'s #2 never occurs in IDE mode's
  sequence (E24 [live; src `TTImp/Interactive/GenerateDef.idr` 285–316, idris2-lsp `GenerateDef.idr`
  73]).
- **Refine Hole with an ambiguous name**: IDE mode offers the qualified alternatives; the server answers
  no action (F34) and the refusal says so.
- **Make With on a hole alone below its clause's `=`**: IDE mode rewrites the clause; the server reads
  the hole's line and answers garbage (`?count_rhswith (_)` [live]), so it is not asked.
- **Add Clause after a load with errors**: IDE mode's compiler finds no declaration; the server answers,
  placed after the clauses by M4's rule (the server itself would insert it above them, making them
  unreachable on `Part.idr` [live]).
- **Proof Search without a result**: IDE mode's compiler says so; the server answers nothing, and the
  refusal says so.

## Security

- The server is spawned only through `core/process.ts` (no shell, fully qualified paths, nothing in
  Restricted Mode), from `ServerOptions` as a function, in a trusted workspace folder or a folder the
  consent gate allowed (judged again right before the spawn, started in the real path judged).

  `refineHole`'s `hint`; `repl` text refused by `replCommandRefusal` (E10); the hints of Proof Search
