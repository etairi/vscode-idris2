## Decisions

1. **Plain TypeScript, the panel opened by hand** (Q8, Q9; the user, 2026-10-30): no framework and no
   `idris2.goalPanel.autoOpen`.
2. **The page is a tree of plain objects.** `src/webview/view.ts` builds an element tree from a
   `PanelState` (`panelView`) and `draw` applies it through a small `DocumentLike`, so all of it runs
   in unit tests on Node, with no DOM library and no jsdom. A state replaces the whole page; the
   Refine input's text, for as long as the same hole is shown, and the focus survive it. The stale
   banner always has its place, so that nothing moves when it appears.
3. **What the webview sends names what it was shown, never a place.** A button, a premise's name, a
   row of a `version`. The host keeps the document and the positions (`state.ts` `PanelTargets`) and
   checks every message (`host.ts` `isFromWebview`). So text in the panel, or a page that went wrong,
   cannot make the host act on anything but the state it sent, and the five toggles are the only
   settings the panel can write.
4. **The panel keeps its own place.** While a webview has the focus VS Code has no active text editor
   [live, e2e], so the host remembers the last Idris editor, and commands run through
   `EditingRegistration.run` with explicit arguments: `EditingCommandArgs` (with `hint`, Refine's
   expression), `EditingRunOptions.choose` (Intro's choices, drawn in the panel) and `.doc` (Next
   Result). A jump passes that editor's `viewColumn`, or it opens in the panel's group.
5. **Next and the buttons follow the hole shown; Save follows the file shown.** With a hole pinned in
   another file, Next is offered for the pinned hole's file and continues there, and the banner and
   its Save are about the file the panel names at its top (*Review*).
6. **Lists stop at 200 holes and 100 messages**, and say how many more there are (`state.ts`): a
   package's holes can be many, the state is sent as a whole, and the Holes view has them all.
7. **The second key leaves the chat input alone.** The Default Keybindings document lists
   `workbench.action.chat.sendToNewChat` on `shift+cmd+enter` when `chatInputHasText && inChatInput`,
   and the chat input is a code editor (CLAUDE.md, M0), so `editorTextFocus &&
   idris2.isIdrisDocument` holds there while an Idris file is active. `cmd+shift+enter` has
   `!inChatInput` in its `when` clause, which ROADMAP's "inside Idris editors only" asks for. The
   letter `,` has the same clause as the other letters.

## Deviations from ROADMAP §5 M7

- **Types are plain text**, without the spans of `:type-of`. ROADMAP says "where available";
  `:metavariables` has none (F2), and they would cost one more compiler request per hole shown.
- **No codicons:** the buttons are text, so that there is no font to bundle and the Content-Security-
  Policy stays minimal.
- **A stylesheet file instead of a nonced `<style>`:** `style-src ${cspSource}`, no nonce (ARCHITECTURE
  §9 as planned had both).
- **No `pinned` and `theme` messages:** `pinned` is part of the state, and the theme is VS Code's
  `--vscode-*` variables, which change by themselves. The one message from the host is `state`.
- **`rendered`, added to the webview's messages:** it acknowledges a version and carries the page's
  text, which is how the tests see that the script ran and what it drew.
- **`hole` and `message` replace `jump`:** a row and a version instead of a URI and a position (*Decisions* 3).
- **Copy is Markdown only**, no `format`.
- **Toggles are settings, and no `:get-options`:** the settings say what is on, and the sessions are
  told (*Printing options*). So an option changed by hand in the compiler's REPL is not this one.
- **The hole on the cursor's line counts** when it is the only one there, beyond "the hole at the
  cursor": at the end of `f x = ?h  -- todo` the panel would be empty otherwise.

## Printing options

Settings `idris2.ideMode.showImplicits`, `showMachineNames`, `fullNamespace` (`IDE_MODE_DISPLAY_KEYS`,
a change restarts nothing), and the existing `idris2.lsp.*` over idris2-lsp; the panel's toggles write
the settings of the backend serving the file, to the workspace when it has a value there.

- **IDE mode.** A new `check` or `shadow` process is told the options that are on, as first requests
  (`SessionDeps.firstRequests`, read for each process; a `shadow` session's `(:enable-syntax :False)`
  stays first). A change is sent to the processes that have a running state (`sendDisplayOptions`):
  only what changed. An `:error` answer or a lost request is logged. **Never the `eval` session**
  (M3: nothing but evaluations goes to it), so evaluations print as before.
- **A change checks the visible documents again**, whatever `idris2.checking.trigger` says
  (`recheckVisible(undefined, true)`), and the active one's unsaved text (`UnsavedChecks.recheck`):
  the user asked for it, and it shows in no other way. Over idris2-lsp, `workspace/didChangeConfiguration`
  goes first, and the panel has the followed file's holes listed again (`HoleModel.relist`).

## Limitations

- **Binders.** Case Split and Jump need a binder the clause model finds on a left-hand side. The
  alternative of a `case` on the clause's own line (`f n = case n of m => ?h`) has none, nor has an
  implicit the left-hand side does not name (`test/unit/editing.test.ts`).
- **Make With and Make Case are not in the panel**, as ROADMAP's list of buttons has it.
- **A printing option changed with the focus in the panel** does not re-check unsaved text until the
  editor is active again, by M6's rule that only the active editor's document is checked while typing.
- **Over idris2-lsp** a changed option re-lists the followed file's holes only; another file's follow
  at the next load.
- **Buttons act on the newest state.** A click that crosses a state not drawn yet (the debounce of a
  move a moment before) acts on the newer hole. M4's checks still hold for it.
- **The capabilities are those of the file followed**, also for a hole pinned in a project on another
  backend. A command that the backend lacks answers `Unsupported`.

## Open issues

- A review by someone other than the author.
- **A stale banner seen once.** In the first full e2e run the page's first text had *The file changed
  since the compiler last read it* right after the check, for a file with no edit. That run's first
  test failed on another assertion, so nothing recorded the status. The test now prints the status
  and asserts `stale: false`, which has held in every run since. The cause was not found; the banner
  reads the same status as the language status item.
- **VS Code sometimes goes on naming the editor as active.** With the panel's group active and the
  panel on top, `window.activeTextEditor` stayed the editor: logged by `focusPanel` in one of the last
  three e2e runs [live]. Three of the 19 runs before them had timed out on it, up to 30 s, with one
  command, with the command repeated every 100 ms, and with the side bar focused first; another
  left the text after `workbench.action.files.revert`, so that the next test found no hole, likely
  the same state [not shown]. Why it happens in some runs only was not found. VS Code recomputes the
  active text editor at some events only, and takes an editor with the text focus first
  (`_updateState`, 1.144.0 [src]), which would leave it stale [inference]. It is not the extension's
  doing: the four `showTextDocument` calls of `src/` all run on a user's command [src], and no tab
  appeared in the panel's group. In real use it would change nothing, since the buttons pass their
  document. The test waits for the panel's group and tab, logs an editor VS Code still names, and
  restores the file with an edit.
